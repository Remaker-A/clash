## 三、具体是怎么设计的

### 3.1 从"场景绑定"到"独立 Agent" ⭐

这是这个项目最关键的一次设计决策 —— **做减法**：

| 剔除项 | 说明 |
|---|---|
| **所有场景元素** | 尤其是"和帐篷有关的情景设定" |
| **所有物理传感器交互** | 温度、湿度等硬件传感数据 |
| 定位 | 变成"**完全独立的软件 Agent**" |

**为什么这么改**：场景绑定（帐篷、传感器）会让 Agent 只能在特定情境下工作，是个**演示品**；剥离之后才是**通用产品**。

### 3.2 人格化设计 ⭐

用户明确要求从**角色 Agent（character agent）** 的角度审视：

> 「你再从一个更有个性、这个 **character agent** 这种角度来看一下，我现在这个 Agent 有哪些可以提升的地方」

关注维度：
- **个性（personality）** —— 不是工具人，是有性格的角色
- **语气与表达** —— 一致性
- **互动感** —— 让用户感觉在和"一个人"交流

### 3.3 工程完整性校验

因为是从别处提取的代码，第一步做了**完整性检查**：

> 「检查一下这个 Agent 的文件是否完整可以运行，因为我是从别的文件里提取出来这个 Agent 相关的代码」
> 「检查一下，现在有配置 API key 吗？直接运行测试一下」

即：**先验证能跑，再谈优化** —— 合理的推进顺序。

## 五、复盘

1. **做减法比做加法难** —— 剔除场景和传感器绑定，才让 Agent 从演示品变成通用产品。
2. **角色 Agent 的核心是"个性"而非"能力"** —— 陪伴类产品里，一致性的人格比功能列表更重要。
3. **迁移代码先验完整性** —— 提取的代码第一件事是跑通 + 检查 API key 配置，避免在坏基础上优化。
