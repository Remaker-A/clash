## 一、项目做了什么

**一句话**：给 TapNow（AI 商业视觉创作平台）做线上智能客服 Agent，负责它的**稳定性、知识库召回、幻觉防护和自动化评测闭环**。

用户咨询范围覆盖：账号登录、订阅计费、退款、AI 生成功能、模型使用、画布操作、常见故障。

项目的推进脉络很清晰，是典型的「**先救火 → 再治本 → 最后建体系**」三步走：

| 阶段 | 时间 | 核心动作 | 解决的问题 |
|---|---|---|---|
| **1. 探索与知识库建设** | 04-15 ~ 04-17 | 用 Claude Code + CLI-Anything 全面探索产品，产出结构化知识库 | Agent 不知道产品有什么功能 |
| **2. 红队与问题定位** | 04-17 ~ 04-30 | 设计攻击/爆破测试集，抓取线上日志做 bad case 分析 | 不知道 Agent 到底哪里不行 |
| **3. 工程重构** | 05-06 ~ 05-14 | 渐进式披露改造、测试工程搭建、LLM Judge 校准、并发压测 | 响应慢、误拒、幻觉、无法回归 |

## 二、用了什么技术

### 2.1 Agent 运行时底座

底层不是自研框架，而是基于开源的 **`nanoclaw`**（一个通用 Coding Agent 容器框架，源自 Claude Agent 体系）：

- **容器化 Agent Runner**：每个会话在独立容器里跑 Agent 循环
- **IPC 文件通信**：容器 ↔ 主进程通过 `data/ipc/<group>/` 下的 JSON 文件收发消息
- **Groups 机制**：`nanoclaw/groups/global/CLAUDE.md` 是 system prompt 的落地点
- **Claude Agent SDK**：工具注册、tool call 调度

### 2.2 模型接入

|---|---|
| Agent 主模型 | 通过 `pincc.tamaredge.host` 网关代理的 Claude（Opus 4.6 等） |
| LLM Judge | 同一网关，独立配置 |
| 环境变量 | `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` |

### 2.3 代码检索与工具链

- **CLI-Anything**（HKUDS 开源）：把 `~/tapnow-source` 源码生成 CLI harness，让 Agent 能"探索"产品
- **DOMShell MCP + Chrome 扩展 + Playwright**：通过 DOM 操作真实探索 `https://app.tapnow.ai`
- **服务端**：VM（`***REDACTED-IP***` / `***REDACTED-IP***:8788`），`/chat` HTTP 接口
- **数据层**：ADB MySQL + Qwen gateway

### 2.4 测试工程（`tests/`）

## 三、具体是怎么设计的

### 3.1 知识库：从「全量加载」到「渐进式披露」⭐

这是整个项目**最核心的一次架构改造**。

**改造前的问题**：

```
容器内 Agent 每次 Read 72KB 全量 KB 文件
→ 每个请求 input 高达 24K tokens
→ 慢、贵、且模型容易被无关内容干扰
```

**改造方案**：拆成 **4 个按需检索工具**，通过 IPC 调用。

| 工具 | 用途 | 信息密度 |
|---|---|---|
| `kb_list_categories` | 列出所有分类（约 7 个） | 最粗 |
| `kb_list_in_category` | 列某分类下所有 Q&A 标题 | 中 |
| `kb_search` | 关键词搜 Q&A 标题，**只返摘要不返答案** | 中 |
| `kb_get` | 按 id 取一条完整答案 | 最细 |

**关键设计**：`kb_search` 只返回 `{id, question, keywords}`，Agent 看到 5 条候选后**自己决定**取哪条再调 `kb_get`。Agent 一次拿不到全文，但能精准定位 —— 这就是渐进式披露。

**实现分层**（新建 `src/kb-service/`，约 400 行）：

| 文件 | 职责 |
|---|---|
| `kb-loader.ts` | 加载 KB，schema 扩展支持 `aliases` / `category` / `related`（向下兼容） |
| `bm25.ts` | BM25 检索，tokenize 时把 `aliases` **一起索引** —— 同义词召回是关键 |
| `kb-index.ts` | 内存索引三合一：`Map<id>` + `Map<category>` + `Bm25Index` |
| `kb-tools.ts` | 4 个工具的实现 |
| `ipc-handler.ts` | 监听 `data/ipc/<group>/kb-requests/`，调度并写回 |

**IPC 协议扩展**：

```
data/ipc/<group>/
  ├── kb-requests/<request_id>.json    容器 → 主进程
  └── kb-responses/<request_id>.json   主进程 → 容器
```

**热加载**：监听 KB 文件 mtime，30s 内自动 rebuild 索引，**不重启服务**。

**提示词侧强约束**：移除"Read 全量 KB"指引，改为「**必须**通过 `kb_search` / `kb_get` 访问，**未调用 `kb_get` 不允许引用具体内容**」—— 从机制上堵死靠记忆编造。

> **效果**：单请求 input 从 24K tokens 降到 **< 5K**，节省 80%+。

### 3.2 幻觉防护：四层组合式护栏 ⭐

客服场景**风险最高**的是「编造内部处理动作」—— 模型为了安抚用户，会虚构工单号、专员、电话、退款状态。

设计成四个层次：

1. **前置识别高风险情绪**
   命中投诉、举报、法律手段等信号 → **直接引导人工客服**，不让模型在高压对话里"自由发挥"。

2. **工具权限收敛**
   原框架默认暴露大量开发类工具，模型会误以为"我能执行后台操作"。收敛到最小集合：
   - ✅ 保留：知识库读取、关键词搜索、基础回复
   - ❌ 移除：命令执行、文件写入、任务派发、浏览器
   —— 既减少"假装行动"的诱因，也降低越权风险。

3. **回复后规则引擎审查**
   检测高风险表达：长数字工单号、虚构专员、400 电话、脱敏手机号、`已为您提交/升级/联系` 等**动作声明**。
   命中 → 替换为安全升级话术。

4. **观测落库**
   幻觉命中结果写入日志字段，供统计、告警、复盘。

> 本质：把「靠提示词约束」升级为「**提示词 + 运行时策略 + 输出审查 + 数据观测**」的组合防护。

### 3.3 ReAct vs RAG 的路线抉择

这是一个很有意思的反复权衡，值得记下来：

- **最初**：用 **ReAct**（Agent 自主多轮工具调用）
- **问题**：**太慢**，对客服这种高频、问题相对标准的场景显得"大材小用"
- **尝试 RAG**：又发现**太难维护**，链路长、bad case 难归因
- **最终方案（用户拍板）**：

> **保留 ReAct 的 Agent 形态，但不要 RAG。知识库检索改为「渐进式披露 + 按需检索」。**

并且把系统**解耦成两部分**，分别输出两份文档：

| 文档 | 读者 | 内容 |
|---|---|---|
| 工程同学的文档 | 工程师 | 原来怎样 → 现在改成什么 → 标准是什么 → 为什么这么改（**刻意不列大量代码**） |
| 业务同学的文档 | 运营/业务 | 知识库内容如何优化 |

### 3.4 测试体系：三层评测 + LLM Judge 校准 ⭐

**测试目标**（用户明确定义的三大类）：

1. **知识库回复能力**
   - 能否准确基于知识库回复
   - 知识库没有的内容，**严禁编造**
2. **回答质量与稳定性**
   - 准确率、成功率
   - 严禁频繁 System Error / 超时
   - 长对话下避免幻觉
3. **内容输出控制**：严禁输出与客服业务无关的内容

**核心工程细节**：

| 问题 | 设计 |
|---|---|
| **LLM Judge 过严** | 原本打 3 分即判 failure → 用户要求"站在客服 Agent 角度审核标准是否过严"，参考 OpenAI / Google / Anthropic 研究后重新设计评分逻辑 |
| **测试集规模** | 数百条：知识库功能用例 + 真实 bad case 回归 + 红队用例 |
| **误判修复** | 多次出现"Agent 输出内容其实是对的，却被判 fail"，逐轮排查是**测试标准有漏洞**而非模型问题 |
| **稳定性** | 并发阶梯测试 `3,5,10,20,30,50`，沙箱安全（不跑 80/100） |
| **Dashboard 同步** | 每次改测试逻辑都要同步可视化看板 |

**并发性能分析**（05-13）：
用户实测 20 并发 ≈ 10 秒、50 并发 ≈ 20 秒，追问根因。结论指向：**上游模型响应 + 容器冷启动 + ReAct 多轮调用**的叠加，而非单纯后端排队。

### 3.5 线上问题定位方法论

**用真实日志说话**（04-30）：

1. 拉取 **16 天线上客服请求日志**，清洗分类
2. 把 bad case 整理成表格清单 → 导出 Markdown 供分享
3. 再做**问题分类汇总**：不只罗列 case，而是提炼「问题类型 + 原因」
4. 用 **Canvas 可视化**渲染全量数据

**关键发现**：一次生产变更后，失败率和平均耗时明显上升。拆解出的影响因素：
- 容器超时策略
- Agent 冷启动
- ReAct 多轮工具调用
- 知识库全文读取（→ 这就是渐进式披露改造的直接动因）
- 上游模型响应

> 这一步的价值：把「客服体验不好」这种模糊问题，转化为**可追踪、可排序、可验证**的工程问题。

### 3.6 误拒治理

原安全规则**误伤正常业务问题**。精细化调整：

| 处理 | 问题类型 |
|---|---|
| 🔴 继续拦截 | 内部探测、运行环境、配置文件、命令执行 |
| 🟢 放行 | "TapNow 有什么能力"、"如何写好提示词"、"退款规则" |

**高频意图快速兜底**：对「人工客服」「转人工」「退款规则」等标准化场景，**直接返回确定性话术**，不进完整 Agent 容器链路 —— 既降延迟，又减少敏感场景的自由发挥空间。

## 四、项目成果（数据）

- 基于真实日志建立 bad case 分析体系，**600+ 条请求**分类复盘，沉淀 **100+ 条**高价值样本
- 单请求 token 从 **24K → < 5K**（节省 80%+）
- 高风险问题拆解为幻觉 / 超时 / 误拒 / 知识缺失 / 工程参数错误五类，形成可执行优化路线
- 从「人工感觉变好」变为「**有数据、有报告、有回归门槛**」

## 六、复盘：这个项目最值得借鉴的三件事

1. **先量化再优化** —— 没有 600+ 条真实日志分类，所有优化都是拍脑袋。
2. **渐进式披露 > 全量塞入** —— 让 Agent 按需检索，比把知识库全丢进上下文又便宜又准，还顺带降低了幻觉。
3. **测试标准本身也需要被测** —— 多次出现「模型答对了但判 fail」，最后发现是 Judge 标准有漏洞。评测体系要能自我修正。
