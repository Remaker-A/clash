## 一、项目做了什么

**一句话**：一个**本地优先（local-first）** 的「急救副驾 Agent」—— 在急救这种紧急场景下，用**本地运行的模型**给出实时判断和指导。

**为什么强调"本地优先"**：急救场景可能发生在无网络、弱网络环境（野外、事故现场），且涉及隐私与生命，**不能依赖云端可用性**。

## 二、用了什么技术

### 2.1 本地模型：Gemma + LiteRT-LM ⭐

| 项 | 内容 |
|---|---|
| 模型 | **Gemma 4 E2B-it** |
| 运行时 | **LiteRT-LM**（Google 的端侧推理运行时） |
| 模型路径 | `models/gemma/gemma-4-E2B-it-litert-lm/gemma-4-E2B-it.litertlm` |

选择 Gemma E2B 这类**小参数端侧模型**，是为了在本地设备上低延迟运行。

### 2.2 技术栈

| 层 | 选型 |
|---|---|
| 运行时 | Node.js（**ESM**） |
| 环境 | Windows + **PowerShell**（路径含中文和空格 —— 这是个坑） |
| 验证 | `npm test` / `npm run verify:local` |

### 2.3 语音链路

独立的 **STT（语音识别）工作流**，专门设为 "Worker B" 负责，有严格的**文件归属边界**。

## 三、具体是怎么设计的

### 3.1 多 Worker 并行协作架构 ⭐

这个项目采用了一种很特别的开发模式：**多 worker 并行 + 主 agent 审核**。

> 「你是『Worker B』，负责 FirstAid Copilot 项目的**语音 / STT 链路**工作流。这是多 worker 并行协作，主 agent 会做质量审核和全量回归，**你必须严格遵守文件归属边界**。」

设计要点：
- 每个 Worker 负责一条独立链路（如语音、STT）
- **严格文件归属边界** —— 避免并行冲突
- 主 agent 负责**质量审核 + 全量回归**

### 3.2 工作流隔离：Git Worktree

用 `git worktree` 建立独立工作树，避免多 worker 互相污染。

### 3.3 Live 模式设计 ⭐

用户提出的核心体验要求：

> 「打开 App **自动开始收声**，而不是需要你去点击。而且这个反应需要比较快。」

改进方向：

| 原方案 | 目标方案 |
|---|---|
| 手动点击开始 | **打开即自动收声** |
| 问完等一会儿 | **问他，马上就能收到反应**（Live 模式） |
| 有视频 Live 设计方向 | 补足设计缺陷 |

> 急救场景下，**每一秒的点击和等待都是成本** —— 这是体验设计的出发点。

### 3.4 验证与测试

- `npm test` —— **20/20 通过**
- `npm run verify:local` —— 通过（但有警告）
- **真实 Gemma 文字流程测试**：通过文字 prompt 输入，让**真实的** Gemma（LiteRT-LM）做出判断和反应，按急救主线流程走一遍，输出**逐阶段报告**

> 注意：强调"真实"—— 不用 mock，走真模型。

## 六、复盘

1. **本地优先是场景倒逼的选择** —— 急救不能假设有网，这决定了整个技术选型（端侧小模型 Gemma E2B + LiteRT-LM）。
2. **多 Worker + 文件归属边界** 是并行开发的有效范式 —— 但必须配主 agent 做质量审核与全量回归。
3. **交互延迟就是体验本身** —— 在急救场景，"打开即收声"比"功能多"重要得多。
4. **测试要走真模型** —— 强调"真实 Gemma 流程测试"而非 mock，才能真正暴露端侧推理的问题。
