## 一、项目做了什么

**一句话**：一个**节假日酒店与行程规划 App** —— 实时获取酒店房价，结合出行范围的地理位置，**自动规划酒店和行程**。

### 核心需求（用户原话拆解）

| 能力 | 内容 |
|---|---|
| **实时房价** | 多渠道酒店房源实时比价 |
| **地理规划** | 结合出行游玩范围的**地理位置**规划酒店 + 行程 |
| **地图能力** | 接入 **地图 MCP** |
| **多渠道房源** | 包含**评价内容**作为选择参考 |
| **社交内容** | 综合**小红书**等社交媒体内容 |
| **酒店 Provider** | 携程类渠道 + **去哪儿** |

## 二、用了什么技术

| 层 | 选型 |
|---|---|
| **LLM** | 默认 **Kimi K2.5** |
| **地图** | 地图 **MCP**（Model Context Protocol） |
| 酒店数据 | 多 Provider（含"去哪儿"） |
| 社交数据 | 小红书等内容源 |
| 架构 | 前后端分离（有 `/api/hotels/search` 等接口） |

> 值得注意：这是 MCP 在项目里的实际应用案例 —— 用 MCP 协议接入地图能力。

## 三、具体是怎么设计的

### 3.1 多源数据融合 ⭐

这个项目的核心设计是**三类数据源的融合决策**：

```
酒店房价数据（多渠道 Provider）
        +
地理位置 / 地图 MCP（行程动线）
        +
评价内容 + 小红书等社交媒体内容（口碑参考）
        ↓
   综合规划建议
```

**设计价值**：不是简单的"搜酒店"，而是**结合出行范围**做整体规划 —— 房价便宜但离游玩区很远，就不是好选择。这是**位置约束下的多目标优化**。

### 3.2 Provider 架构

酒店数据源做成可插拔的 **Provider** 结构，方便接入不同渠道（携程、去哪儿等）—— 与 EDM 项目的多渠道抽象思路一致。

### 3.3 模型选择

默认 LLM 用 **Kimi K2.5**。

## 六、复盘

1. **规划的难点在"约束融合"** —— 房价、位置、口碑三者往往互相冲突，产品价值就在于综合权衡。
2. **Provider 化是数据源集成的通用解法** —— 与 EDM 的 AI Provider 抽象同一思路：可插拔、易扩展。
3. **MCP 让外部能力集成标准化** —— 地图这类能力用 MCP 接入，比自己封装接口更规范。
4. **外部 API 依赖要有降级预案** —— `404 Not Found` 这类接口问题会直接阻断用户体验。
